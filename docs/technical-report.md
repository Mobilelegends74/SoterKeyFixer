# Soter Key Fixer 1.4 TEST — технический отчёт

## TEST 3: наблюдение с телефона и загрузочный обход

В новом архиве TEST 2 монитор запущен на uptime 15, служба наблюдается `running`
на uptime 36. Автоматический start не требовался. Action на uptime 349
перезапустил выделенную службу: PID 3396 → 30092, бюджет 1/3. По сообщению
пользователя и снимку EngineerMode после Action SOTER получил PASS; очистки данных
не было. Это подтверждает результат этого теста, а не исправление ключевого
материала или гарантированное отсутствие повторного FAIL.

TEST 3 добавляет отдельный режим `boot`: только для OP5D3BL1 / OnePlus / SDK 35
и проверенного безопасного persistent init-профиля. После boot-completed ждём
300 секунд, затем два наблюдения готовности с интервалом не менее 30 секунд.
Неподготовленные зависимости/заблокированный пользователь/`restarting`
откладывают запрос и сбрасывают окно готовности. Запрос единственный, общий
repair.lock и бюджет исключают второй после Action или нового worker. Отказ
init тоже расходует попытку. Режим записывается в status.json и журнал.

Это намеренно обозначенный загрузочный обход, не подтверждённый сбой ключа.
Работающая служба не перезапускается повторно по периодическому таймеру.
`boot-off` выключает только этот обход; `boot-on` включает со следующей загрузки.
Закрытая активная SOTER-сессия не распознаётся. Для первой проверки нужны
перезагрузка, разблокировка и 6–7 минут без Action/платежей, затем EngineerMode.

## Регрессия TEST 1 и исправление TEST 2

Архив OnePlus 13R CPH2645 / OP5D3BL1 / SDK 35 подтвердил: `vendor.soter`
работает, PID 3645, профиль `/vendor/etc/init/vendor.qti.hardware.soter-service.rc`
выделенный, класс `late_start`, бинарник `/vendor/bin/hw/vendor.qti.hardware.soter-service`.
`keystore2` и `vendor.qseecomd` работают, SELinux Enforcing, пользователь разблокирован.

Все три Action остановились до запроса (`0/3`): `cmd package` вернул
`Failed transaction (2147483646)`, а TEST 1 ошибочно счёл это отсутствием Tencent
APK. Наличие/доступность SDK-приложения нельзя делать обязательным условием для
жизненного цикла нативной HAL. В TEST 2 этот барьер удалён; сами запросы пакета
сохранены только в диагностике, вместе с stderr. Ошибка Package Manager пока
не объяснена и не доказывает отсутствия APK. Его данные не очищаются.

Добавлены регрессионные тесты с настоящим init-профилем из архива и точной ошибкой
Binder, а также с отсутствующим/отключённым SDK APK. Лимиты, grace, блокировки,
проверки профиля и зависимостей остаются. Это устраняет отказ до восстановления,
но успешное исправление аппаратного FAIL требует повторного теста на телефоне.

## Почему проверка ключа остаётся непроверенной

`init.svc.vendor.soter=running` — состояние процесса, не подпись/верификация и
не доказательство исправности ATTK/ASK/AuthKey.
[SDK Tencent](https://github.com/Tencent/soter/blob/master/soter-client-sdk/soter-core/src/main/java/com/tencent/soter/core/SoterCore.java)
проверяет ASK/подпись в контексте приложения.
[AIDL](https://github.com/Tencent/soter/blob/master/soter-client-sdk/soter-core/src/main/aidl/com/tencent/soter/soterserver/ISoterService.aidl)
использует UID и содержит также создающие/удаляющие ключи операции.
Ключ root-UID, существование ASK или регистрация Binder/HAL не заменяют заводской
тест OnePlus. В исходном модуле нет документированного безопасного OEM-пробника;
физический OnePlus 13R к среде разработки не подключён.

Не выполняются неизвестные Binder transaction codes, генерация/удаление ключей,
запуск под чужим UID или догадки о кодах закрытого HAL.
`functional_probe=unavailable` означает отсутствие **проверенного пробника в
модуле**, а не отсутствие аппаратного SOTER. Для автоматического контроля FAIL
при `running` нужен подтверждённый read-only OEM API либо валидированный клиент
с правильной идентичностью, разрешениями и ожидаемой криптографической проверкой.

## Автомат состояний

1. Два boot-входа запускают worker в фоне. `watch.lock` оставляет одного владельца.
   Живые inode блокировок не удаляются.
2. Ожидание boot-completed ограничено 600 секундами; поздний hook может повторить
   вход. Создаётся grace 90 секунд для текущего boot ID.
3. Безопасная постоянная выделенная служба наблюдается раз в 120 секунд.
   Стабильное `running` не считается сбоем ключа; отдельно допускается однократный
   загрузочный обход TEST 3 для описанного профиля.
4. `repair.lock` сериализует Action/автомат. Для автостарта нужны три `stopped`
   с интервалами 5 секунд. Повторно проверяются загрузка, CE-разблокировка,
   keystore2/qseecomd, остановка/пауза/обновление модуля. Состояние SDK APK
   диагностируется отдельно и не блокирует нативную HAL.
5. Восстановление `stopped` — `ctl.start vendor.soter`; Action и однократный
   загрузочный обход — `ctl.restart`.
   Атомарный init-запрос не оставляет отдельное окно между stop/start при гибели
   shell. Доступность наблюдается до 20 раз с интервалом 1 секунда.
6. Бюджет резервируется атомарно **до** запроса. Отказ/таймаут тоже расходуют
   попытку. Максимум 3 запроса на boot ID, паузы 300/900 секунд. Новый процесс
   не сбрасывает бюджет; повреждённый бюджет блокирует восстановление.
7. Без смены PID/наблюдаемого перехода ручной запрос помечается UNCONFIRMED.
   Даже при наблюдаемом восстановлении ключ — UNKNOWN_UNVERIFIED.
8. Исчерпание бюджета прекращает авто-вмешательство до перезагрузки.
   Длительное редкое наблюдение не является бесконечным циклом ремонта.

Семантика init: [AOSP](https://android.googlesource.com/platform/system/core/+/refs/heads/android15-release/init/README.md).
`disabled`/`oneshot` могут быть штатным lazy HAL; автостарт исключён. Общие,
критические, неоднозначные профили и побочные init-триггеры отклоняются.

## Совместимость, ресурсы и жизненный цикл

OnePlus/SDK 35 — предварительный фильтр, профиль проверяется отдельно. Имя
службы не подменяется похожим. Неизвестная прошивка получает диагностический отказ.
BusyBox/system applets проверяются по отдельности. Без flock/timeout нет
восстановления. Дочерним timeout/sleep не передаются FD блокировок: тесты
обнаружили и исправили удержание lock таймером BusyBox после завершения команды.
В mksh дескриптор явно передаётся внешнему flock: иначе shell закрывает его
при exec. Эта особенность проверяется отдельным полным прогоном тестов в mksh.
AWK вызывается через BusyBox, если отдельного awk в Android нет.

Один shell + sleep, опрос раз в две минуты, без непрерывного logcat/опроса HAL.
Снимки создаются по запросу или перед ограниченной попыткой. Раннего boot hook,
монтирований, нативных библиотек или изменений SELinux нет.

Disable/Remove/Update/Pause проверяются и перед запросом, и при наблюдении.
Остановка по удалению привязана к boot ID: переустановка с перезагрузкой не
наследует вечный stop. Блокировки освобождает ядро; опасного kill по старому PID
нет. Свои логи остаются для диагностики после удаления.

Нет управления KeyMint/Keymaster, keystore2, QSEE, RKP или StrongBox и доступа к
их данным/сертификатам/Keybox. Внутренние связи закрытого TEE и влияние ручного
перезапуска на активную SOTER-сессию проверяются на телефоне; абсолютное отсутствие
влияния на всю прошивку не заявляется.

## Проверки и следующий этап

Тестовые Android-команды существуют только в harness. Настоящие flock/timeout
проверяют конкуренцию, boot-дубликаты, повторные процессы, cooldown/бюджет,
перезагрузку, повреждение состояния, отказ в контроле, lazy/critical/shared
профили, паузу/удаление/обновление, редактирование настроек во время попытки и
отсутствие ложного подтверждения по неизменившемуся `running`.

Сборщик проверяет allowlist файлов ZIP, ID SoterFix, versionCode 16 (TEST 3), права,
контрольную сумму. Тесты/CI/локальные данные в ZIP не попадают. GitHub workflow
публикует только artifacts. Успешный CI не доказывает аппаратное восстановление.

На телефоне нужны результаты EngineerMode до/после Action, повторение после
сна и перезагрузки, диагностический архив и проверка прежней аутентификации.
Если FAIL остаётся при `running`, нужен разбор vendor-протокола/журнала;
периодические перезапуски и очистка данных не подменяют такое доказательство.
